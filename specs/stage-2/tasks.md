## Review batches

- **Batch 1** (`T10`) — builds on: none. Data model and derived-balance functions
  (`held`/`available`/`effective_status`), fixture/reset/`GET /me` additions. Everything
  else that touches money or holds needs this first.
- **Batch 2** (`T16`) — builds on: none. Shared visual system, content-negotiation helper,
  and the retry/sequencing/formatting JS module every screen wires into. **Batch 1 and
  batch 2 share no files and no runtime dependency on each other — both can be developed and
  reviewed in parallel starting from stage-2's first revision (`8acf008`).**
- **Batch 3** (`T11,T12,T13,T14,T15`) — builds on: batch 1. The full authorization API
  surface (create, capture, void, list) plus switching the three existing affordability
  checks from `balance` to `available`. Grouped together because every task here reads or
  writes the same `authorizations` data structure batch 1 introduced, and T15's correctness
  can only be demonstrated once T11 can actually create a hold to test against.
- **Batch 4** (`T17,T18,T19,T20`) — builds on: batch 1, batch 2. The non-authorization
  screens (signup/login, balance/pay, requests, split) — each needs the shared UI module
  (batch 2) and the `available`/`held` fields (batch 1) for display, but none of them call
  any authorization endpoint directly, so this batch does not need batch 3 merged first.
- **Batch 5** (`T21,T22`) — builds on: batch 1, batch 2, batch 3, batch 4. The
  `/authorizations` screen needs every authorization endpoint (batch 3) and the shared UI
  module (batch 2); export/import v2 needs the full model (batch 1) and `authorization_id`
  on payments (batch 3's T12). Grouped together as the stage's closing slice.
