## Review batches

- **Batch 1** (`T23`) — builds on: none. The payment-revision/`balance_view` foundation:
  data model, reset validation, the one shared balance function every later task calls.
- **Batch 2** (`T24`) — builds on: none. The authorization historical-hold model:
  generalizes stage-2's `effective_status`/`held`/`available` to take `(as_of, known_at)`,
  proven equal to the stage-2 functions at `(now, now)`. **Batch 1 and batch 2 touch
  disjoint files (`src/ledger.py`+payment fields vs. `src/authorizations.py`+authorization
  fields) and neither calls the other's new code, so both can be developed and reviewed in
  parallel starting from stage-3's first revision (`84158ac`).**
- **Batch 3** (`T25`) — builds on: batch 1, batch 2. `GET /me`'s `as_of`/`known_at` wiring
  needs both the payment-side balance function and the holds-side `held_view` to answer
  R276's combined `total`/`available`/`balance` view.
- **Batch 4** (`T26`, `T27`) — builds on: batch 1 only. `GET /statement` never involves
  holds (R288), so this slice needs only the payment-revision foundation and can proceed
  independently of batch 2/3 once batch 1 merges. T27 (selected-revision ordering, snapshot
  pagination) is grouped with T26 (base statement) because they share `src/statements.py`
  and T27 extends T26's same entry-building code rather than introducing a parallel path.
- **Batch 5** (`T28`, `T29`) — builds on: batch 1, batch 2. Corrections need both the
  payment-side revision/balance machinery (append a revision, run the boundary sweep) and
  the holds-side `held_view` (R284's `available` leg of `historical_overdraft`); export/import
  needs both sides' storage fields to round-trip. Grouped as the stage's closing slice,
  touching `src/corrections.py` and `src/testctl.py` respectively — no file overlap between
  the two, but neither has further work downstream, so batching them avoids a sixth batch.
